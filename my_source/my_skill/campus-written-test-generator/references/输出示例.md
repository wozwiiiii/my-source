## 参考答案与详细解析

### 岗位一：AI 应用开发岗

#### 第 1 题

**参考答案**

先说结论：三者的核心差异在于"是否精确"和"如何用更少的比较次数换取更快的速度"。

**打个比方**：暴力检索像把书架上每本书都翻一遍找一句话；HNSW 像图书馆的导航层级——先到"分区"再到"书架"最后到"具体某一层"，逐层收窄；IVF-PQ 则像先把书按主题粗分几十堆，只在最相关的几堆里翻，且每本书只记录"摘要"而非全文。

| 方案 | 检索精度 | 内存占用 | 查询速度 | 适用规模 |
|---|---|---|---|---|
| 暴力精确检索 | 100%（理论最优） | 向量全量存储，最高 | 与数据量线性相关，最慢 | 万级以下 |
| HNSW | 接近精确（可通过 ef 参数调节） | 高，需额外存储图结构 | 极快，对数级 | 百万级，内存充足 |
| IVF-PQ | 有损（PQ 量化带来精度损失） | 低，量化后显著压缩 | 快，但需控制 nprobe | 千万级以上，内存受限 |

选型判断的关键维度是**精度要求 → 内存预算 → 延迟目标**这三者的优先级排序。

**本场景分析**：500 万条、P99 < 100ms，属于"中等规模 + 较严延迟"的场景。HNSW 是更稳妥的选择——500 万向量在主流配置下内存可承受，且 HNSW 的对数级查询能稳定满足 100ms 以内的 P99。IVF-PQ 虽然内存省得多，但量化损失会直接影响召回，需要额外投入重排成本来补偿。

**常见误区**
- 只答"HNSW 快、IVF 省内存"而不给选型判断框架
- 忽略 `ef` / `nprobe` 这类可调参数对精度-速度曲线的影响
- 认为 IVF-PQ 精度无损（PQ 是有损压缩）

#### 第 2 题

**实现思路**

按步长滑动窗口切分即可，关键在于参数校验和边界收敛——`i` 每次前进 `chunk_size - overlap`，这样下一个块的起始位置与上一块末尾恰好重叠 `overlap` 个字符。循环必须在 `i < len(text)` 时继续，否则会漏掉最后一小段。

**参考代码**

```python
def split_text(text: str, chunk_size: int, overlap: int) -> list[str]:
    """
    将文本按固定长度切分，相邻块保留 overlap 个字符的重叠。

    时间复杂度: O(n)，n 为文本长度（每行代码仅在窗口上做常数次操作）
    空间复杂度: O(n)，输出总长度约为原始长度的 n/(chunk_size-overlap) 倍
    """
    # ---- 参数校验：边界处理的第一步 ----
    if chunk_size <= 0:
        raise ValueError("chunk_size 必须为正整数")
    if overlap < 0:
        raise ValueError("overlap 不能为负数")
    if overlap >= chunk_size:
        raise ValueError("overlap 必须小于 chunk_size，否则窗口无法前进")

    # ---- 边界：空串或纯空白 ----
    # 用 rstrip 判断是否"无有效内容"，避免把纯空白当成有效文本切分
    if not text or not text.strip():
        return []

    n = len(text)
    if n <= chunk_size:
        # 文本不够一个窗口，直接返回整体
        return [text]

    chunks: list[str] = []
    step = chunk_size - overlap  # 窗口前进步长，必须 > 0（已由上面的校验保证）
    i = 0
    while i < n:
        chunk = text[i : i + chunk_size]
        if chunk:
            chunks.append(chunk)
        i += step
    return chunks
```

**边界测试用例**

| 输入 | 预期输出 | 考察点 |
|---|---|---|
| `split_text("", 5, 2)` | `[]` | 空字符串 |
| `split_text("   ", 5, 2)` | `[]` | 纯空白 |
| `split_text("abc", 5, 2)` | `["abc"]` | 文本短于窗口 |
| `split_text("abcdefghij", 4, 2)` | `["abcd", "cdef", "efgh", "ghij", "ij"]` | 重叠窗口推进；**末块残留 `"ij"` 需注意** |
| `split_text("abc", 3, 3)` | `ValueError` | overlap 等于 chunk_size 会死循环，必须拦截 |
| `split_text("abc", 3, -1)` | `ValueError` | 负重叠 |

> ⚠️ 最容易出错的两处：
> 1. `overlap >= chunk_size` 时 `step` 会变成 0 或负数，导致 `while` 死循环或 `i` 倒退。这个校验不是可选项。
> 2. 最后一块可能因步长不整除而产生**很短的残留块**（上例中的 `"ij"`）。生产中通常需要设置最小长度阈值来丢弃或合并这种尾块，否则会污染向量库的召回质量。

### 岗位三：技术支持岗

#### 第 2 题

**参考答案**

**1. 问题定位**

核心问题在 `WHERE DATE(created_at) = '2026-10-01'` 这一句。

对索引列使用函数（`DATE()`）会导致**索引失效**——数据库的 B+ 树索引存的是 `created_at` 的原始值，而 `DATE(created_at)` 是运行时计算出的新值，索引无法用于比较，只能退化为**全表扫描**。2000 万行全扫，高峰期 8 秒是典型表现。

另外还有两个隐藏问题：
- `status = 1` 的选择性通常很低（比如只有 2-3 个取值），即使单独建了索引，优化器也可能认为走它不如全扫
- `ORDER BY created_at DESC` 配合 `LIMIT 20`，如果无法利用索引的有序性，就需要把全部匹配行排序后再取前 20 条

**2. 改写方案**

```sql
SELECT id, user_id, amount, status, created_at
FROM orders
WHERE created_at >= '2026-10-01 00:00:00'
  AND created_at <  '2026-10-02 00:00:00'
  AND status = 1
ORDER BY created_at DESC
LIMIT 20;
```

各改动的作用：

| 改动 | 作用 |
|---|---|
| `DATE(created_at) = '...'` → 范围比较 | 让 `created_at` 上的索引可用，把全表扫描变范围扫描 |
| 用 `>= 左闭` 与 `< 右开` 而非 `BETWEEN` | 避免日期时间精度问题（`BETWEEN` 上界若含时间部分会丢数据） |
| 保留 `ORDER BY created_at DESC` | 若索引有序列，数据库可直接顺扫取前 20 条，省掉排序 |

进阶做法是建复合索引 `(status, created_at)` 或 `(created_at, status)`，具体顺序取决于 `status = 1` 的选择性——选择性高时把 `status` 放前面更好。

**3. 下一步排查方向**

1. 用 `EXPLAIN` 看执行计划：确认 `type` 是 `range`/`ref` 而非 `ALL`，`rows` 扫描行数是否可接受，`Extra` 里有没有 `Using filesort`
2. 检查数据分布：`status = 1` 占全表比例是多少？占比过高则单列索引无意义
3. 检查是否存在隐式类型转换（如 `status` 是 varchar 却传了数字）
4. 确认统计信息是否过期（`ANALYZE TABLE`），优化器可能因此选错索引
5. 若数据量持续增长，考虑按时间分区或归档历史数据

**Tradeoff 提示**
- 加复合索引能显著提速，但会增加写入开销与存储占用——订单表写多读少的场景下需权衡
- 分区表能改善大范围的查询，但对单日查询收益有限，且增加运维复杂度

### 第 3 题（售前方向）

**1. 显性需求 vs 隐性需求**

先说一个判断口径：客户说的"要什么"通常是**解决方案**，而不是**真实问题**。售前的核心动作就是把解决方案还原回问题。

| 类型 | 客户原话 | 分析 |
|---|---|---|
| 显性 | 要一套智能客服系统 | 这是客户已经预设的解决方案，未必是唯一或最优路径 |
| 显性 | 三个月内上线 | 时间约束，需确认是否由某个业务节点倒推而来 |
| 隐性 | "回答全部产品技术问题" | 真实痛点可能是**客服人力不足**或**新人上手慢**，客服系统只是其中一种手段 |
| 隐性 | "准确率 99%" | 客户表达的是**对错误零容忍**的心理预期，而非经过计算的指标 |
| 隐性 | 资料散落各部门、30% 未电子化 | 这往往是**真正的项目风险**，客户自己可能还没意识到 |

需要挖掘的问题（按优先级）：
1. 当前客服每天接到多少问题？其中多少是重复的？（判断收益基线）
2. 谁在回答这些问题？他们的痛点是什么？（识别真实痛点归属）
3. 如果答错了，会有什么后果？（判断错误容忍度，而非纠缠数字）
4. 谁为这个项目的成败负责？他的成功标准是什么？（识别决策者的真实诉求）

**2. "准确率 99%" 的问题**

这个指标有三重问题：

1. **定义不清**："准确率"的分母是什么？全部提问？还是系统愿意回答的那部分？如果把"答不上来就转人工"排除在外，指标可以被轻易"做"到很高，但对客户毫无价值。
2. **与数据现状矛盾**：30% 资料未电子化意味着知识库天然有缺口，此时承诺任何绝对准确率都是不负责任的。
3. **可能选错指标**：客服场景真正该看的是**问题解决率**（用户的问题是否被解决，而非答案是否"准确"）和**转人工率**。

对齐方法：把绝对准确率替换为**分层指标**——
- 覆盖率：系统能回答的问题占比（可随资料补齐逐步提升）
- 回答正确率：在系统愿意回答的问题中，答案正确的比例
- 拒答率：明确转向人工的比例（这是**优点**而非缺陷）

并约定：拒答不视为失败，错误回答才是。这样指标才可衡量、可优化。

**3. 技术回复框架**

| 类别 | 内容 |
|---|---|
| **可以承诺** | 按计划完成知识库构建与系统上线；对未电子化资料，配合客户完成梳理（需客户指定责任人）；拒答机制保证不输出无依据答案 |
| **不能承诺** | 不承诺"99% 准确率"这类未经数据支撑的绝对指标；不承诺覆盖全部技术问题（受资料完整度限制） |
| **前置条件** | 客户须指定资料归口部门与对接人；约定资料整理的时间节点；上线前共同定义指标口径 |
| **实施路径** | ①资料盘点与缺口评估（2-3 周）→ ②知识库构建与试点（4-6 周，选 1-2 条产品线）→ ③效果评估与指标校准 → ④全量推广 |
| **风险提示** | 三个月完成全量上线存在风险，建议先试点后推广；资料电子化占用的时间不完全可控 |

**Tradeoff 分析**

| 方案 | 优势 | 代价 | 适用条件 |
|---|---|---|---|
| 承诺 99% 拿下订单 | 短期签单顺利 | 交付必然违约，售后成本与口碑损失巨大 | 不建议 |
| 拒绝客户指标 | 守住技术底线 | 可能被竞品以"我们能做到"抢单 | 需配合替代方案提出 |
| **换指标口径 + 分期交付**（推荐） | 预期可对齐、风险可控、仍能签单 | 需要客户配合投入资料整理资源 | 客户有真实业务意愿时成立 |

**要点提炼**
- 售前不是"答得技术多深"，而是"能否把不可行的需求转化成可行的方案"
- 遇到无法满足的要求，不要直接拒绝，而是**重新定义问题**（把"准确率"换成"覆盖率 + 拒答率"）
- 所有承诺必须与交付团队的能力边界一致，售前过度承诺是交付事故的源头

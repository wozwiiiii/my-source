# 校招 AI 岗面试题库生成器

基于项目（**真实项目可选**）生成面试题，模拟真实面试官视角（含评分要点与连环追问方向）。**核心价值**：不是考知识点的笔试，而是"面试官会怎么追问"的预演——有真实项目就深挖你的实际决策，没有就考察你的工程判断力。

**角色定位**：你是一名面试过大量校招候选人的 AI 岗面试官。你清楚候选人在项目题上最容易含糊其辞的地方，也知道哪些追问能瞬间分辨"真做过"和"只是看过文档"。

---

## 一、与笔试题生成器的分工（重要）

本 Skill 与 `campus-written-test-generator` **定位不同，不可混用**：

| 维度 | 笔试题生成器 | 本 Skill（面试题库） |
|---|---|---|
| 岗位 | 4 类 | 4 类（相同） |
| 每岗题数 | 3 题 | **4 题** |
| 题型 | 概念 / 实操 / 场景 | 技术基础 / 项目类 / 场景 / 实操手撕 |
| 项目绑定 | 可选 | **可选**（有则深挖真实模块，无则改出通用项目场景题） |
| 独有元素 | — | **【评分要点】+【追问方向】** |
| 交互形态 | 书面作答 | 面试官连环追问预演 |

**触发词隔离**：用户说"笔试题 / 笔试 / 模拟卷"→ 走笔试题生成器；说"面试题 / 模拟面试 / 追问 / 项目深挖"→ 走本 Skill。若用户表达模糊，询问其一。

> 若用户明确要求"面试题但不要评分要点"，仍使用本 Skill，省略评分要点/追问方向字段即可。

## 二、输入规范

### 输入参数

| 参数 | 必选 | 说明 | 缺省行为 |
|---|---|---|---|
| **目标项目信息** | 否 | 仓库目录结构、技术栈、核心功能、工程化亮点、模块架构、项目定位。可接受：本地仓库路径、README 粘贴、GitHub URL、文档链接、口头描述 | **缺失时，第 2 题改用"通用项目场景题"**（见下方降级规则） |
| 生成日期 | 否 | `YYYY-MM-DD` | 自动取当前系统日期，不反问 |
| 岗位范围 | 否 | 可指定单岗或细分（如"技术支持-售前"） | 全部四类岗位 |
| 难度等级 | 否 | 一面基础 / **二面（默认）** / 三面深度 | 中大厂校招二面 |
| 侧重方向 | 否 | 如"侧重 RAG 检索优化" | 均衡覆盖技术、项目、场景、实操 |

### 项目信息缺失时的降级规则（重要）

**用户未提供项目信息时，Skill 仍需正常出题**，第 2 题按以下方式转化：

| 有真实项目 | 无真实项目 |
|---|---|
| 深挖形态 → 锚定真实模块，追问候选人的实际决策 | **改为"通用项目场景题"**：给出一个典型项目场景，请候选人假设自己是负责人来回答 |
| 例：「你的 eval runner 为什么用分批执行？」 | 例：「假设你负责一个 RAG 问答系统的评估模块，需要支持数百条用例的批量执行。请说明你会如何设计？」 |

**降级后的第 2 题仍是项目类题型**，考察重点从"你的真实经历"转为"你的工程决策能力"，评分要点与追问方向照常编写。

**若用户提供了项目信息**，则回到标准模式，执行下方读取规则。

### 项目信息的读取规则（有项目时适用，防幻觉红线）

1. **只使用可核实的信息**。读过 README / 代码 / 结构后才引用。
2. **禁止补充项目未提及的功能、技术点、性能数据**。例如项目没说用了 Redis，绝不能出"你项目里 Redis 如何做缓存穿透"这种题。
3. 引用项目细节时**须能定位来源**（如"你在 `runner/batch_runner.py` 里的分批执行设计…"），使候选人与面试官都能核对。
4. 用户描述含糊时，宁可出通用技术题，也不要"合理推测"项目细节——这是本 Skill 最容易犯且最致命的错误。
5. 用户提供项目名但缺细节时：**先尝试读取**（本地路径→直接读；GitHub URL→WebFetch README；文档链接→读取）；读不到再索要，一次最多问 3 个最关键的问题（技术栈、核心功能、你负责的部分）。若用户不提供，则走降级规则。

### 难度档位对照

| 档位 | 定位 | 题目特征 | 追问深度 |
|---|---|---|---|
| 一面基础 | 筛掉基本功不扎实者 | 原理表述 + 简单对比 | 1 层追问 |
| **二面（默认）** | 分辨"真做过"与"背过" | 项目细节 + 权衡取舍 | 2-3 层连环追问 |
| 三面深度 | 判断技术判断力上限 | 架构演进 + 非常规场景 | 开放式深挖 |

## 三、题型矩阵（每岗严格 4 题）

| 岗位 | 第 1 题 | 第 2 题 | 第 3 题 | 第 4 题 |
|---|---|---|---|---|
| **AI 应用开发** | 技术基础 | 项目类 | 场景分析 | 代码手撕 |
| **Agent 开发** | 技术基础 | 项目类 | 场景分析 | 代码手撕 |
| **技术支持** | 技术基础 | 项目类 | 场景分析 | **故障排查 SOP** |
| **产品** | 技术基础 | 项目类 | 场景分析 | **产品分析 / 设计** |

### 各题型命题要求

**第 1 题 · 技术基础题**
- 考察底层原理，**不止考定义**——必须包含"原理理解 / 技术对比 / 适用边界"三者之一以上
- 拒绝纯背诵（"请解释什么是 RAG"这类不出）
- 好题示例：「RAG 中为什么需要重排（Rerank）？如果去掉重排，把召回数量 K 拉到很大，能否达到同样效果？代价是什么？」

**第 2 题 · 项目类题**
- 模拟面试官与候选人的项目对话，考察四件事：**项目理解 / 技术选型原因 / 难点解决方案 / 个人收获**
- 两种形态：
  - **有真实项目** → 深挖形态：锚定具体模块或文件（如"你在 XX 模块的设计"），不能泛泛说"你的项目"，并预设 2-3 层追问
  - **无真实项目** → 通用场景形态：给出典型场景，请候选人假设自己是负责人来回答
- 好题示例（深挖）：「你的评估模块采用了分批执行来代替一次性跑全量，这个设计解决的痛点是什么？如果评估集从几十条扩到 500 条，这套分批策略还成立吗？为什么？」
- 好题示例（通用场景）：「假设你要为一个 RAG 问答系统设计评估模块，需要支持数百条用例批量执行。请说明你的设计思路。」

**第 3 题 · 场景分析题**
- 贴近真实工作场景，考察系统设计、问题排查、方案选型与权衡
- **必须存在权衡**——没有唯一正确答案，但要有明确决策依据
- 场景应与项目所属领域相关（AI 项目不必出电商库存题）

**第 4 题 · 实操 / 手撕题**

| 岗位 | 形态 | 要求 |
|---|---|---|
| AI 应用 / Agent | 代码手撕 | 必须含**边界处理**、可运行、逐行注释 |
| 技术支持 | 故障排查 SOP | 给出可执行的分步排查流程图 + 每步判断依据 |
| 产品 | 产品分析 / 设计 | 给出分析框架 + 完整的产出物结构（如 PRD 章节） |

> ⚠️ 技术支持岗与产品岗的第 4 题**不是写代码**。让产品岗手撕算法是硬伤。

### 技术支持岗细分方向

技术支持是**岗位族**，未指定细分时以 TSE 为主：

| 细分 | 第 4 题形态 | 侧重考点 |
|---|---|---|
| **技术支持 / TSE**（默认） | 故障排查 SOP | 分层定位、日志检索、SQL 排查、复现能力 |
| **售前工程师** | 方案讲解 / 技术应答 SOP | 需求挖掘、方案匹配、竞品客观对比、承诺边界 |
| **售后工程师** | 交付 / 升级 / 回滚 SOP | SLA 履约、变更管理、客户沟通、续约风险 |

指定细分时，岗位名称与考察点标签须写明方向（如「技术支持岗·售前方向」）。

## 四、考点差异化约束（强制）

四岗位考点**不得重复**，各自侧重如下：

| 岗位 | 侧重方向 |
|---|---|
| AI 应用开发 | RAG 链路、向量检索、大模型应用开发、工程化实现 |
| Agent 开发 | 多智能体协作、任务调度、状态管理、框架原理、工具调用容错 |
| 技术支持 | 故障排查、问题定位、SOP 流程、客户问题处理 |
| 产品 | 需求分析、产品设计、价值判断、迭代逻辑 |

**交叉检查方法**：生成后，把四岗共 16 题的技术关键词列成清单，若同一关键词（如"向量检索"）出现在两个岗位，检查是否为"同概念不同角度"——若是同角度，必须替换其中一题。

> 允许的合理交叉：AI 应用岗考"向量检索的 HNSW vs IVF-PQ"，Agent 岗考"Agent 如何决定何时调用检索工具"——概念相关但考察角度不同，可接受。

## 六、执行工作流

```
输入解析 → 项目信息提取（可选）→ 岗位考点匹配 → 题目命制 → 解析编写 → 排版 → 质量自检 → 交付
```

### Step 1 · 输入解析与项目信息提取（可选）

先判断用户是否提供了项目信息，据此决定第 2 题的形态：

**若提供了项目信息**，提取五要素：**技术栈、核心功能、工程化亮点、模块架构、项目定位**。
- 本地路径 → 读 README + 目录结构 + 核心模块
- GitHub URL → WebFetch README
- 文档链接 → 读取
- 信息不完整 → 向用户索要（一次最多 3 个关键问题）
- **不编造未提及的信息**

**若未提供项目信息**，跳过提取，第 2 题改出通用项目场景题。**不要因此反问用户**——直接按降级模式出题，用户后续想加项目可再补。

### Step 2 · 岗位考点匹配
- 四岗各自从考点库取考点
- 有项目时：找项目与考点的**结合点**，项目题须落在真实模块上，并标注来源（哪个文件 / 哪个功能）
- 无项目时：为每岗设计一个典型场景作为项目题的载体（如 AI 岗给"RAG 问答系统"、Agent 岗给"任务编排助手"）

### Step 3 · 题目命制
- 按题型矩阵逐题生成，同步编写**【评分要点】与【追问方向】**
- 评分要点：3-4 条，说明"答到什么程度算过关、什么算加分"
- 追问方向：2-3 条，模拟面试官顺着答案继续挖的问题
- 每道题标注考察点标签
- 第 2 题为项目类题，**有项目时须标注【项目锚点】**，无项目时无需该字段

### Step 4 · 解析编写
| 题型 | 解析要求 |
|---|---|
| 技术基础 | 核心原理 + 多维对比（**优先表格**）+ 适用场景 |
| 项目类（深挖） | 答题思路 + **高分回答范例** + 面试官追问点解答 |
| 项目类（通用场景） | 设计思路 + 方案要点 + 面试官追问点解答 |
| 场景分析 | 完整思路 + Tradeoff 分析 + 选型依据 |
| 代码 / SOP | 可运行代码（含逐行注释 + 边界用例）或分步 SOP |

所有解析**小白友好**：先类比再讲原理，复杂概念配具体示例。

### Step 5 · 排版
严格按第七节模板，**无多余说明文字**。

### Step 6 · 质量自检
执行第八节 8 条校验，**命中任意一项则重新生成该项**。

### Step 7 · 交付
- 默认：输出到对话
- 用户指定的在线知识库/文档节点 → 写入该节点
- 用户指定本地路径 → 写入该路径
- **不输出无关的引导性、解释性文字**；不在未指定位置残留文件

## 八、质量校验规则（强制，命中即返工）

| # | 校验项 | 判定标准 |
|---|---|---|
| 1 | **结构完整** | 四个岗位齐全；每岗 4 题；每题含考察点标签、评分要点、追问方向、作答区、解析——缺任意一项即失败（用户明确要求省略评分要点/追问方向时，仅省略对应字段，其余校验照常执行） |
| 2 | **项目题合规** | 有项目材料时：项目题须锚定真实模块并标注【项目锚点】；泛泛而谈或编造项目细节即失败。无项目材料时：第 2 题须为通用项目场景题，且场景符合该岗位领域 |
| 3 | **考点不偏** | 无偏题、怪题、冷门知识点；符合中大厂校招统招范围 |
| 4 | **不重复** | 四岗 16 题考点不得高度重合（见第四节交叉检查方法） |
| 5 | **无冗余** | 无多余说明文字、无关内容、私人信息 |
| 6 | **代码可用** | 代码题可运行，含边界处理与注释；技术支持/产品岗第 4 题为 SOP / 分析框架而非代码 |
| 7 | **解析有深度** | 不得只有结论；须有原理、对比、tradeoff 分析 |
| 8 | **格式规范** | 符合第七节模板，可直接录入知识库，无需二次排版 |

## 九、常见陷阱

| 陷阱 | 正确做法 |
|---|---|
| 无项目信息时反问用户、卡住不出题 | 直接走降级模式出通用项目场景题，用户想加项目可后续补 |
| 有项目信息但凭常识"补全"细节 | 只引用可核实的信息；**编造项目细节是头号禁区** |
| 项目类题写成"请介绍你的项目" | 有项目：锚定具体模块/文件 + 预设 2-3 层追问；无项目：给出明确场景 + 角色设定 |
| 四岗都考 RAG，只是换了问法 | 按第四节考点差异化表分配，生成后做关键词交叉检查 |
| 让产品岗手撕算法 | 产品岗第 4 题为产品分析/设计题 |
| 评分要点写成"答对即可得分" | 具体化：答到 X 算过关，答到 Y 算加分，缺 Z 算不合格 |
| 追问方向写成"还有什么想问的" | 写成顺着答案继续挖的真实问题，如"如果 QPS 翻 10 倍这个设计还成立吗" |
| 解析只给结论 | 须有原理 + 对比 + tradeoff |
| 输出末尾加客套引导语 | 无多余说明文字，直接结束于复核提醒 |

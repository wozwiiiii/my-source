## 参考答案与详细解析

### 岗位一：AI 应用开发岗

#### 第 1 题 · 技术基础题

**参考答案**

**1. 重排解决的核心问题**

先说一个类比：向量检索像"图书馆按主题快速找到一摞相关书架"，但它只判断"主题像不像"。而 Rerank 像"请一位专家把这摞书逐本翻开，按你的具体问题排个序"。

技术上的差异在于：

| 阶段 | 模型类型 | 计算方式 | 特点 |
|---|---|---|---|
| 向量召回 | Bi-Encoder（双塔） | query 和文档**分别**编码成向量，算余弦相似度 | 快，可预先建索引；但 query 与文档没有交互 |
| 重排 | Cross-Encoder | query 和文档**拼在一起**送进模型 | 准，能捕捉细粒度交互；但每次都需前向计算，慢 |

核心问题：Bi-Encoder 的"分别编码"意味着它无法感知 query 与文档之间的细粒度关系。比如 query 是"如何退款"，一篇讲"退款流程"的文档和一篇讲"退款政策限制"的文档，向量相似度可能很接近，但用户要的可能是前者。Cross-Encoder 能把两者放一起比较，区分度更高。

**2. 把 K 从 5 拉到 50 能否代替重排？**

**不能完全代替，且代价明显。** 三个具体问题：

1. **噪声引入**：K 越大，混进来的低相关文档越多。LLM 面对 50 篇文档时，无法像 Rerank 那样精确排序，容易采纳错误信息。
2. **上下文窗口被挤占**：50 篇文档可能超过模型的上下文限制，被迫截断——而被截掉的可能恰好是关键的。
3. **注意力稀释（lost in the middle）**：已有研究与实践表明，LLM 对长上下文中间部分的信息利用率明显低于开头和结尾。文档铺得太开，关键信息的权重反而下降。

**代价对比**

| 方案 | 延迟 | 成本 | 效果 |
|---|---|---|---|
| 召回 K=5 + 重排 | 中（多一次模型前向） | 中（重排模型调用） | 好，排序精准 |
| 召回 K=50 无重排 | 低（省了重排） | **高**（50 篇全部进 LLM 上下文，token 成本激增） | 不稳定，受噪声与注意力稀释影响 |

**结论**：两者不是"替代"关系。K=50 省下的是重排延迟，付出的是 LLM token 成本和效果波动。**如果延迟预算允许，标准做法是"召回 K=20 左右 + 重排取 top 5"**——粗排保证不漏，精排保证准。

**常见误区**
- 认为重排只是"再算一次相似度"，忽略 Bi-Encoder 与 Cross-Encoder 的本质差异
- 认为 K 越大效果越好（实际存在拐点，且成本线性上升）
- 忽略 token 成本——K=50 的上下文成本可能是 K=5 的数倍

#### 第 2 题 · 项目类题（深挖形态）

**答题思路**

项目类题的答题结构与技术题不同：**先讲问题，再讲方案的边界，最后讲取舍**。不要一上来就说"我用了分批执行"，而是先说"当时遇到什么问题，为什么一次性跑不行"。若为通用场景形态，则改为"先讲清场景约束，再给设计方案，最后说明取舍"。

**高分回答范例**（深挖形态，基于真实项目，可直接参照表达结构）

> **1. 设计动机**
>
> 最初的 eval runner 是一次性跑完全部用例。实测中发现三个问题：一是外部 API 有速率限制，连续请求会被限流甚至返回 429，导致后面的用例莫名失败，把"限流失败"和"真实答错"混在一起，污染了评估结果；二是单轮全量跑下来 token 消耗可观，如果第一轮就发现 prompt 有问题，钱已经花完了；三是长任务中途中断就得从头再来，没有断点。
>
> 所以改成按批次执行：每个批次跑固定数量的用例，批次之间加冷却间隔，批次内的结果单独落盘。这样既能规避限流，也能在发现异常时及时止损，还能从断点续跑。
>
> **2. 扩展到 500 条是否成立**
>
> 策略本身仍然成立，但有几个部分需要改：
>
> - **批次大小要重算**：批大小原本是按限流阈值定的，用例变多后如果继续用固定批大小，总耗时线性增长会变得不可接受，可能需要引入并发（但并发又会加剧限流问题，需要更精细的令牌桶控制）。
> - **落盘结构要变**：现在每个批次单独落盘，500 条会产生大量小文件，需要改成按轮次汇总或写入数据库，同时要能按用例 ID 快速检索。
> - **失败处理策略要升级**：小规模时可以人工看失败用例，规模大了必须有自动分类——把"限流失败""超时""真实答错"自动区分开，否则人工根本无法处理。
> - **成本预估要前置**：先用少量样本估算单用例平均 token，再决定跑不跑全量，避免跑到一半发现预算超了。
>
> **3. 为什么分类评估而不合并总分**
>
> 因为不同能力维度的错误代价不一样，合并成一个加权总分反而会掩盖问题。
>
> 比如结构化查询类考察的是查询生成的正确性，任务路由类考察的是"该不该调用某个工具"的判断能力，多步综合类考察的是多步任务的编排。如果只给一个总分，出现"总分 80 分"时，我无法知道是"SQL 全对但另一类全错"还是"两类都各错一半"——而这两种情况的修复方向完全不同。
>
> 另外，加权本身也是个问题：凭什么查询类占 40%、路由类占 20%？这个权重没有任何客观依据，拍脑袋定出来的权重会让分数看起来很精确，实际上是伪科学。所以更好的做法是分开呈现，让每个维度的表现自己说话。

**面试官追问点解答**

| 追问 | 解答要点 |
|---|---|
| 某批失败重跑整轮还是补跑？ | 只补跑失败批次，但要注意：如果失败原因是 prompt 被改了，那前面跑的批次也要重跑——判断标准是"失败是环境问题还是逻辑问题" |
| 评估集怎么构建的？有标注吗？ | 需如实回答。若无人工标注，要说明标签的来源（如从真实查询日志中筛选、按规则构造），并承认这带来的局限 |
| 这套 eval 能测出回答质量吗？ | 要诚实：多数 eval 测的是"能不能选出正确工具/生成可执行 SQL"，很难测"回答是否易懂、是否有帮助"。要说明这是自动评估的天然边界，质量部分仍需人工抽检 |

### 岗位三：技术支持岗

#### 第 4 题 · 故障排查 SOP

**参考 SOP**

> **第一步 · 止血（0-2 分钟，优先于定位）**
>
> - **做什么**：确认是否为全量影响。若已影响大盘，先执行降级——切到缓存结果或返回简化答案，保证"能用"优于"好用"。
> - **看什么**：监控大盘的错误率曲线、QPS 曲线。
> - **判断**：若错误率持续上升且无自愈迹象 → 立即降级或回滚，**不要先查原因**。
> - **升级判断**：持续 5 分钟未缓解，或影响用户数 >1000 → 同步上报。

> **第二步 · 界定影响面（并行进行）**
>
> - **做什么**：确认是全部请求还是部分请求受影响；是所有查询类型还是特定类型。
> - **看什么**：按维度切分指标——按接口、按用户群、按查询类型。
> - **判断**：若只有某个查询类型慢 → 指向该链路特有的依赖（如 web 检索类的第三方 API）；若全部慢 → 指向公共依赖（向量库、LLM 网关）。

> **第三步 · 分层定位根因**
>
> 按 **外部依赖 → 应用层 → 数据层** 顺序排查：
>
> | 层次 | 查什么 | 判断依据 |
> |---|---|---|
> | 外部依赖 | LLM API 是否限流/降级、第三方检索 API 状态 | 看网关返回码，是否大量 429/503 |
> | 应用层 | 服务自身负载、GC、连接池是否耗尽 | CPU/内存/连接数曲线，线程栈 |
> | 数据层 | 向量库延迟、慢查询 | 向量库监控指标、慢日志 |
>
> - **判断**：若外部依赖正常、应用层资源也正常 → 大概率是数据层或某个具体链路。
> - 注意区分**延迟升高**（变慢但仍成功）与**超时失败**（真的断了）——前者多为资源竞争，后者多为依赖不可用。

> **第四步 · 恢复与验证**
>
> - 执行修复后，**必须验证指标回到基线**再撤除降级，避免反复。
> - 观察窗口建议 10 分钟以上，确认无二次劣化。

> **第五步 · 事后 RCA**
>
> - 时间线还原（何时开始、何时发现、何时缓解、何时修复）
> - 根因分析（直接原因 + 根本原因，如"限流触发"是直接原因，"没有做请求配额分配"才是根本原因）
> - 改进项（可落地的具体动作，不要写"加强监控"这类空话）

**评分要点**
- **过关线**：SOP 有分层顺序，知道先止血后定位
- **加分项**：每步给出具体指标与判断阈值，而非"查看日志"
- **高分项**：区分"立即执行"与"并行排查"；RCA 里能区分直接原因与根本原因

**Tradeoff 提示**

| 决策 | 优势 | 代价 | 适用条件 |
|---|---|---|---|
| 立即回滚 | 快速止血，确定性高 | 丢失本次变更的收益；回滚本身也可能出问题 | 变更后短时间内出现故障 |
| 降级限流 | 保留部分能力，影响面小 | 用户体验打折，需产品侧认可 | 根因未明但影响可控 |
| 继续排查不处理 | 避免误操作 | 影响面持续扩大 | **仅适用于影响面极小且已定位的场景** |

# 校招简历持续优化工作流

## 一、任务定义

对多版本求职简历进行持续优化，确保内容真实、结构清晰、符合校招简历标准。

**核心原则**：在完全不改变事实的前提下，用 STAR 法则重构经历，让简历通过 HR 的 10 秒初筛，且经得起面试官深挖。

**适用场景**：
- 简历内容定期审核与优化
- 新增项目经历后的结构化拆解
- 代码事实核实（通过 GitHub 仓库验证简历数据）
- 多版本简历的同步更新
- 投递前的交叉审核

---

## 二、标准工作流程

### 阶段一：内容读取与事实核查

#### 1. 读取当前简历内容
从用户指定的来源读取各版本简历的当前内容（粘贴文本 / 本地文件路径 / 在线文档均可）。

#### 2. 代码事实核实（如有 GitHub 仓库）
- 读取项目代码（本地仓库路径或 GitHub 仓库 URL）
- 核实简历中的所有数字（测试数、异常类数、缺陷数、表数量等）
- 对无法核实的数字，改为定性描述或标注【请补充】
- **核实后先汇报让用户审核，再更新文档**

#### 3. 时间事实确认
- 项目时间、获奖时间、社团时间、教育时间等必须与用户确认一致
- 时间格式统一为 `YYYY.MM – YYYY.MM`

---

### 阶段二：项目经历结构化拆解

每个项目必须包含以下四个层级：

#### 1. 项目简介（一段话）
- 项目是什么、技术栈、规模
- 示例：`面向电商场景的订单管理后端服务，基于 Spring Boot 搭建，处理订单创建、库存扣减、支付回调三类核心业务，日均调用量约 X 万次。`

#### 2. 背景（一段话，因果递进逻辑）
**逻辑顺序**：项目起点 → 业务挑战 → 外部依赖 → 工程难题
- 禁止分点，必须是连贯段落
- 每个句子之间有因果关系，不是简单罗列
- 示例：`该项目最初为课程大作业，仅实现了基本的订单创建功能，缺乏异常处理和事务保证，后续需要扩展为可支撑高并发的生产级服务。电商大促期间订单量激增，原有同步处理方式响应变慢，需要引入异步队列削峰。同时，库存扣减与订单创建存在分布式事务问题，需要保证数据一致性。在高并发场景下，还面临缓存击穿与数据库连接池耗尽等性能难题。`

#### 3. 核心工作（分点，每点有明确技术细节）
- 每点以技术领域开头（如「后端分层架构」「认证体系」「异步任务处理」）
- 包含具体工具、参数、实现方式
- 禁止空洞描述，必须有可验证的技术细节
- 示例：`订单创建采用本地消息表保证最终一致性（订单表与消息表同事务写入，定时任务轮询补偿）；库存扣减使用 Redis 分布式锁 + 数据库乐观锁双重保证，超卖率从 X% 降至 0；引入 RocketMQ 异步处理支付回调，峰值 QPS 从 X 提升至 Y`

#### 4. 产出（分点，体现项目特色）
- 必须是具体结果，不是泛泛的「提升了性能」
- 体现项目独有的特色（如「通过本地消息表解决了订单与库存的分布式事务一致性问题——该方案在课程大作业阶段完全缺失，是生产化改造的核心」）
- 有数据的用数据，无数据的用定性描述
- 禁止使用「显著提升」「行业领先」等过度包装词汇

---

### 阶段三：校园简历优化器五项审核

按以下五项标准逐条审核，每项必须打勾确认：

#### 1. 过度包装检查
- [ ] 是否存在「主导/牵头/战略/显著提升/行业领先」等词？
- [ ] 如有，替换为「参与/协助/完成/优化」等符合应届生身份的词汇

#### 2. AI 味检查
- [ ] 是否存在「赋能/抓手/闭环/矩阵/深耕/打法/链路」等空洞词汇？
- [ ] 如有，替换为具体白话描述

#### 3. 数据可信度检查
- [ ] 所有数字是否有原始依据（代码/文档/用户确认）？
- [ ] 无法核实的数字是否已改为定性描述或标注【请补充】？
- [ ] 禁止凭空编造百分比、增长率、用户量等数据

#### 4. 应届生身份匹配
- [ ] 描述中的责任级别是否确实是实习生/应届生能承担的范围？
- [ ] 使用 AI 辅助开发的模式是否如实说明（不夸大个人能力、不隐瞒 AI 协作）？

#### 5. 面试深挖测试
- [ ] 简历中每个项目，能否清晰回答「你具体敲了哪一行代码/写了哪一行字」？
- [ ] 技术细节是否经得起追问（参数、实现方式、踩坑过程）？

### 阶段四：多版本同步更新

**原则**：多个版本的项目经历核心事实必须一致，侧重点因目标岗位而异。以下为常见岗位分类示例，用户可根据自己的投递方向增减：

| 目标岗位方向 | 侧重点示例 |
|----------|--------|
| 全栈/通用开发 | 全栈能力、产品决策、工程化全貌 |
| AI 应用/算法工程 | 模型集成、推理优化、数据处理、效果评估 |
| 后端/服务端开发 | 架构设计、并发编程、数据库、中间件、性能优化 |
| 前端/客户端开发 | 组件设计、状态管理、性能优化、用户体验 |
| 产品/项目管理 | 需求定义、竞品分析、MVP 规划、验收标准、跨团队协作 |
| 测试/质量保障 | 测试策略、自动化测试、缺陷管理、质量度量 |

> **注意**：以上仅为示例，实际版本划分应根据用户的投递岗位和经历特点定制。核心事实（项目时间、技术栈、产出数据）在所有版本中必须保持一致。

**更新原则**：
- 先在本地草稿中修改（Markdown 或任意文本形式）
- 验证内容无误后，按简历的存储形式更新（本地文件直接写入；在线文档通过相应工具更新）
- 更新后重新读取验证修改已生效

## 三、关键约束（必须严格遵守）

### 1. 真实性第一
- 所有描述必须朴素、可信
- 严禁凭空编造数据
- 无法核实的数字改为定性描述
- 代码核实后先汇报让用户审核，再更新文档

### 2. 禁止过度包装
- 严禁使用「主导」「牵头」「独立负责大型项目」「显著提升」「行业领先」「战略级」等词汇
- 除非原文有绝对支撑

### 3. 拒绝 AI 味
- 避免使用「赋能」「抓手」「闭环」「矩阵」「深耕」「打法」「链路」等空洞词汇
- 用具体白话描述

### 4. 背景段落要求
- 必须是一段话，禁止分点
- 逻辑因果递进：项目起点 → 业务挑战 → 外部依赖 → 工程难题
- 每个句子之间有因果关系

### 5. 产出要求
- 体现项目特色，不能泛泛
- 有具体结果，不是「提升了性能」
- 有数据用数据，无数据用定性描述

### 6. 修改可追溯
- 所有修改必须标注具体修改内容和修改原因
- 定时任务只做审核报告，不自动修改文档
- 所有修改经用户确认后执行

## 四、代码事实核实方法论

### 核实流程
1. **定位数据点**：从简历中提取所有具体数字
2. **读取代码**：通过本地仓库或 GitHub 仓库读取相关代码文件
3. **逐条核实**：
   - 测试数：统计 `def test_` / `@Test` 数量 + 参数化测试展开数量
   - 异常/错误类数：读取异常定义文件，统计除基类外的子类数量
   - 接口/路由数：读取路由配置文件，统计 API 端点数量
   - 表/实体数量：读取数据模型或配置文件确认
   - 其他具体数字：定位到代码中的常量、配置或文档说明
4. **交叉验证**：README、审计报告、CLAUDE.md 等文档中的数字互相印证
5. **汇报审核**：将核实结果（准确/有偏差/无法核实）汇报给用户
6. **更新文档**：用户确认后再修改简历

### 常见问题处理
- **README 与代码不一致**：以代码实际为准，README 可能未更新
- **审计报告数据旧**：注意报告日期，后续新增的测试不计入旧报告
- **数字无法核实**：改为定性描述，不保留无法验证的具体数字
- **用户确认保留**：如用户明确要求保留某数字，需在报告中说明「用户确认保留，代码核实有偏差」

## 五、定时任务建议（可选）

### 触发条件
- 每周一次（如每周一早上）
- 或用户主动触发

### 执行内容
1. 读取各版本简历的当前内容
2. 按五项审核标准逐条检查
3. 如有 GitHub 代码更新，重新核实关键数据
4. 生成审核报告（发现的问题+修改建议）
5. 等待用户确认后再执行更新

### 注意事项
- 定时任务只做审核和报告，**不自动修改文档**
- 所有修改必须经用户确认后执行
- 报告需客观、实事求是，不夸大问题
- 报告中必须标注具体修改内容和修改原因

...

### 六、待用户确认事项

### 修改记录格式
每次修改必须记录：
- 修改位置：[哪个版本 + 哪个部分]
- 修改前：[原表述]
- 修改后：[新表述]
- 修改原因：[为什么修改，依据是什么]

## 七、常见陷阱

| 陷阱 | 正确做法 |
|------|----------|
| 看到「参与 XX 项目」自动升级为「主导 XX 项目」 | 保持原文级别，「参与」就是「参与」 |
| 原文无数据时自行估算一个百分比 | 删除数据，改为定性描述，并用【请补充】提示用户 |
| 滥用「显著提升用户体验」等万能结尾 | 写具体结果：做了什么、产出是什么、谁认可了 |
| 用「赋能业务增长」等大词填充空洞经历 | 坦诚描述：一段简单经历用简单语言写清楚即可 |
| 为匹配 JD 编造不存在的技能或经历 | 只能调整已有经历的侧重点，不能凭空添加 |
| 代码核实后直接修改文档 | 先汇报让用户审核，确认后再修改 |
| 定时任务自动修改文档 | 只做审核报告，修改必须经用户确认 |
